Özet Hüküm

Evet, mümkün ve doğru hamle. Bugün her agent kendi gateway kopyasını açıyor — yani whatsapp, helm, ikas gibi tekil (singleton) servisler bile çoğalıyor. Hedef: makinede tek bir canlı daemon, ağ üzerinden (Streamable HTTP) birden çok agent'a hizmet versin. İşin güzeli: yakın zamanda eklediğin lazy-activate, "süreç canlı" ile "şema context'te" kavramlarını zaten ayırmış — paylaşımlı daemon için gereken en zor ayrıştırma bu, ve büyük ölçüde hazır.

1 Bugün nasıl çalışıyor

Gateway şu an saf bir stdio MCP sunucusu. stdio doğası gereği 1:1'dir: bir süreç, bir ebeveyne pipe'lanır. Yani her agent oturumu kendi gateway sürecini doğurur, o da kendi child'larını.

# Bugünkü gerçeklik — her agent kendi dünyasını kuruyor
Claude oturumu ──stdio──▶ gateway #1 ──stdio──▶ helm,  whatsapp,  ikas …
Codex  oturumu ──stdio──▶ gateway #2 ──stdio──▶ helm', whatsapp', ikas' …   ◀ KOPYA
özel agent     ──stdio──▶ gateway #3 ──stdio──▶ …                            ◀ KOPYA
                                       ▲ aynı tekil servisler N kez doğuyor

Tek bağlantı, paylaşılmayan state

  • Transport: sadece StdioServerTransport. src/index.ts:85
  • Tek Server örneği, oturum/bağlantı kavramı yok. src/index.ts:32
  • State tamamen bellekte ve global: states + connections Map'leri. Süreçler arası hiçbir paylaşım yok. src/child-manager.ts:9-10
  • Her ListTools global registry'yi döner — çok-client'ta bir client'ın "full mode"u diğerinin context'ine sızar. src/index.ts:42-44 · registry.ts:41
  • Kapanışta tüm child'lar ölür (SIGINT/SIGTERM → shutdown). Daemon kalıcılığı yok. src/index.ts:72-82 · child-manager.ts:554
Asıl Sorun — sadece israf değil, hata

Config'indeki servislerin çoğu makine-tekili: whatsapp (tek WhatsApp Web oturumu), helm (gerçek Chrome'u sürüyor), ikas-direm (tek OAuth token), biletix (DISPLAY :1). Bunları paralel iki kopyada çalıştırmak yanlış — oturum çakışması, kilitli profil, token yarışı. Yani paylaşımlı daemon bir "nice-to-have" değil, bu servisler için doğru model.

2 Neden yolun %70'i bitmiş

Lazy-activate refaktoru farkında olmadan paylaşımlı-daemon için gereken kritik ayrımı yaptı.

PAYLAŞILABİLİR (global) ✓

Pahalı, tekil kaynaklar zaten doğal olarak global: canlı child süreç, allTools listesi, health/ping, uptime. Lazy modda gateway süreci canlı tutar ama hiçbir şemayı context'e enjekte etmez. child-manager.ts:168-179

OTURUMA ÖZEL (per-session) ◑

Tek client'a özel olan şey küçük: hangi servisi "full mode"a yükselttiğin, yani ToolRegistry'nin ListTools'a dönen şemaları + grup filtresi. Lazy varsayılan olduğu için çoğu oturum bunu neredeyse boş taşır.

Anahtar İçgörü

Çok-client'a geçiş = ağır olan her şeyi global bırak, sadece o küçük "şema görünümü" katmanını oturuma taşı. 559 satırlık ChildManager'ın büyük kısmı aynen kalır. Bu yüzden bu, baştan yazım değil, cerrahi bir ayrıştırma.

3 Hedef mimari

Tek, uzun-ömürlü gateway daemon'u (systemd --user). Canlı child servisleri tutar, ağ üzerinden Streamable HTTP ile birden çok heterojen agent'a hizmet verir.

4 Kritik teknik kararlar

4.1 — Transport: Streamable HTTP

MCP'nin güncel standardı. Tek endpoint, çoklu client, Mcp-Session-Id header'ı ile oturum yönetimi, yanıt içinde SSE stream. SDK'da StreamableHTTPServerTransport hazır. İskelet:

import { StreamableHTTPServerTransport } from "@modelcontextprotocol/sdk/server/streamableHttp.js";
// her Mcp-Session-Id için: kendi Server örneği + kendi SessionView (registry)
// global ChildManager TEK, tüm oturumlarca paylaşılır
app.post("/mcp", handleSession);   // 127.0.0.1'e bind, dışarı kapalı
  • Claude Code: HTTP MCP'yi native destekler — claude mcp add --transport http gateway http://127.0.0.1:PORT/mcp.
  • Codex: HTTP MCP destekliyorsa doğrudan; değilse mcp-remote köprüsü (zaten stitch servisinde kullanıyorsun → stdio→HTTP köprüsü senin için çözülmüş bir kalıp).
  • Özel agent / cron: SDK client ya da düz HTTP.

4.2 — Eşzamanlılık güvenliği

  • Çift-spawn: activate "active mi?" kontrolü ile spawn arası await var; iki eşzamanlı çağrı ikisi de geçip iki süreç açar. Map<name,Promise> in-flight kilidi ile serileştir. child-manager.ts:86,142-166
  • Stateful servis (helm): protokolde eşzamanlı çağrı sorun değil ama tek tarayıcı mantıken seri olmalı → opsiyonel per-servis concurrency=1 kuyruğu.
  • deactivate yarışı: Paylaşımlı dünyada bir agent'ın kapattığı servisi diğeri kullanıyor olabilir → ref-count ya da "deactivate = admin/explicit" kuralı.

4.3 — Daemon yaşam döngüsü

  • systemctl --user unit: login'de başlat, çökünce restart. (Global-tooling kuralınla birebir: "MCP servisleri global gateway'de yaşar.")
  • Child auto-restart + exponential backoff; keepAlive/autoActivate servisleri kendiliğinden ayağa kalksın. Bugün çökünce sadece error işaretleniyor. child-manager.ts:148-158
  • Yapılandırılmış log → journald; stderr daemon'da kaybolur. Her tool çağrısı için audit satırı (kim, hangi servis, hangi tool).
  • Opsiyonel gateway.app durum sayfası: ne canlı, uptime, son çağrılar (senin PROJECT.app alışkanlığına uygun).

4.4 — Kimlik, policy, auth güvenlik ağı

Çok agent ortak havuza bağlanınca, MCP handshake'indeki clientInfo.name ("claude-code", "codex"…) ile her bağlantıyı tanı. Buraya bir allow/deny policy katmanı koy:

whatsapp kuralınla birebir örtüşüyor

CLAUDE.md: "whatsapp asla onaysız göndermesin." Gateway'de policy gate = merkezi emniyet: ör. güvenilmeyen/otomatik bir agent whatsapp.send'e hiç erişemesin, ya da o tool için zorunlu onay bayrağı. Tek tek agent'lara güvenmek yerine kapıda uygula.

Localhost-only başla (127.0.0.1, auth gerekmez). Cihazlar arası (macbook-cagla, fjds) gerekiyorsa: bearer token + Cloudflare Tunnel / SSH tüneli. Adım adım.

1

Çift transport — HTTP ekle additive

StreamableHTTPServerTransport'u stdio'nun yanına koy. GATEWAY_HTTP_PORT env'i varsa HTTP daemon olarak da dinle, 127.0.0.1'e bind. Mevcut stdio davranışı hiç değişmez.

risk: düşük (eklemeli) · değer: daemon iskeleti
2

Görünümü oturuma çek çekirdek refaktor

ToolRegistry + onToolsChanged per-session olur; ChildManager global kalır. call()/tools() global okur, activate(lazy=false) oturuma yazar. Lazy varsayılan sayesinde per-session yük neredeyse sıfır.

risk: orta · değer: gerçek çok-client izolasyonu
3

Eşzamanlılık güvenliği spawnLock

Per-servis in-flight activation kilidi (çift-spawn yok), stateful servisler için opsiyonel seri kuyruk, deactivate için ref-count / admin kuralı.

risk: düşük · değer: çoklu agent altında dayanıklılık
4

Daemonize + süpervizyon systemd

systemctl --user unit, login'de başlat, çökme restart; child auto-restart + backoff; journald log + audit; opsiyonel gateway.app durum sayfası ve /health endpoint'i.

risk: düşük · değer: "hep açık, canlı" hedefi gerçekleşir
5

Kimlik · policy · auth opsiyonel

Per-bağlantı kimlik (clientInfo), agent başına allow/deny policy (whatsapp emniyet ağı), bearer-token auth, cihazlar arası için Cloudflare Tunnel.

risk: düşük-orta · değer: güvenli paylaşım + uzaktan erişim
